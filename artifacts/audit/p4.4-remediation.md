## 1. Fixes made

### 1.1 `must-usage.ts` — diagnostic finding instead of silent PASS (decision 7)

`run()` previously did `if (mustMethods.length === 0) return [];` — the exact failure *shape* as
legacy Rule03/04/05's vacuous-PASS bug. Now emits one `Finding`
(`key: "must-usage:no-subjects-found"`) naming the detection failure explicitly. A new fixture
(`test/fixtures/must-usage/no-subjects-found/`) — a real `src/PineGuard.MustClauses` directory
whose only members deliberately do **not** match the extension-method shape — proves the diagnostic
fires, not an empty array. This path is dormant against the real repo (607 methods are always
found there), so it changes no real-repo count; it is a correctness backstop, not a debt fix.

### 1.2 Fixture-scope leakage — centralised exclusion (decision 8, the highest-priority item)

`engine.ts`'s `buildContext` now filters `apps/cli/**` out of `ctx.trackedFiles` immediately after
`listTrackedFiles`, before any rule reads it. This is the single shared file-scanning scope 12 of
14 rules consume, so the fix reaches `doc-links`, `test-orphans`, and `test-structure` (the three
P4.1 named) without touching those rule files. `test-files` was checked separately — it walks the
physical `<rootDir>/tests` tree directly (never `ctx.trackedFiles`), and `apps/cli`'s own fixtures
live under `apps/cli/test/` (singular), so it was never exposed to this leakage and needed no
change. No other rule computes its own file list independently of `ctx.trackedFiles`/
`listTrackedFiles` against the real repo (the direct-filesystem-walk fallbacks in `test-structure`,
`test-records`, `test-orphans`, and `doc-links` only ever run in the fixture-harness path, where
`ctx.rootDir` is an isolated fixture directory with no `apps/cli` tree to leak from).

### 1.3 `test-files.ts` — widened `[Fact]` detection (decision 1)

`FACT_ATTRIBUTE_PATTERN` changed from `/\[\s*Fact(\s*\(|\s*\])/` to
`/[[,]\s*Fact(?:Attribute)?\s*[(\],]/` — anchoring `Fact`/`FactAttribute` to the *start* of an
attribute-list item (immediately after `[` or a `,` separator) rather than matching the bare word
anywhere, so a string literal that merely mentions "Fact" in an unrelated attribute's argument is
not a new false positive. Catches `[FactAttribute]`, `[FactAttribute(...)]`, `[Fact, Trait(...)]`,
and `[Trait(...), Fact]`. Zero occurrences of any of these forms exist on `main`, confirmed by the
real-repo run below — a zero-new-debt widening, exactly as decided.

### 1.4 `test-records.ts` — removed the `ValueCase<>`/`BaseCase` ban (decision 4)

Deleted `RAW_INFRASTRUCTURE_BASES` and its `"wrong-base"` finding branch. `unit-test.md` §2.2 lists
`BaseCase` and `ValueCase<TValue>` as current, first-class case-hierarchy members — not superseded,
unlike `IsCase<T>`/`HasCase<T>`. The `"missing-base"` check (a case record with **no** base clause
at all) is untouched; only the specific "has a base, but it's the raw infrastructure type" check
was cut. Re-ran the rule's own suite after the change: the one test that exercised this check
(`test-records.test.ts`'s boundary case) now asserts the opposite — a direct `BaseCase` base
produces **zero** findings — and the rest of the suite (which never depended on this check) is
unaffected.

### 1.5 `test-structure.ts` — conditional `NullCases`/`AdHocCases` recognition (decision 5)

Added `isRecognisedDataset(name, groupPropertyNames)`: `NullCases` is recognised only when the same
Operation Group also declares both `ValidCases` and `InvalidCases` (`fixture.md` §12.2's
inverted-guard nullable-variant shape); `AdHocCases` is recognised only when the group also
declares `Cases`, `ValidCases`, or `InvalidCases` (`fixture.md` §11.6: it supplements
RuleScenario-derived cases, never replaces them). Recognised names get check 4's emptiness check;
unrecognised occurrences are silently ignored, exactly as any other unrecognised name is today (no
"unknown dataset name" check exists to flag them) — this is additive, not a behaviour change for
the un-conditioned case. Proven both ways: a new `invalid/` fixture (`FooRulesTestData.IsQux`, with
`ValidCases`+`InvalidCases` present) shows an empty `NullCases => [];` is now caught; a new
`boundary/` fixture (`BoundaryRulesTestData.IsNullOnly`, with **no** co-occurring
`ValidCases`/`InvalidCases`) shows an empty `NullCases => [];` **without** the condition is still
correctly ignored. New `valid/` fixtures (`NullRulesTestData.IsInvertedNullable`,
`IsAdHocFriendly`) prove the correctly-used shapes produce zero findings.

### 1.6 Confirmations (no code change)

- **Decision 2 (`[InlineData]`)**: `unit-test.md` §1 bans it generally, but §11's Enforcement
  section — what `test-files` actually gates — scopes the check to `[Theory]`-only/no-`[Fact]`,
  omitting `[InlineData]`. `test-files` correctly implements what §11 gates today. Recorded as a
  spec-internal gap in the plan (§8.7), not fixed in code — widening it would put 5 new findings
  directly on `test-files`, the one hard CI gate among the five `test-*` rules.
- **Decision 3 (`test-structure` global scope)**: confirmed `unit-test.md` §2.1's "(Other)"
  catch-all requires the same §5.1 structure for every test project, with no per-layer carve-out
  the way `test-records`' base-record convention has one. Kept global; recorded in the plan (§8.7).
- **Decision 6 (Pattern E ordering)**: confirmed no §4.4 record-ordering check exists anywhere in
  `test-structure.ts` or any other rule that would conflict with the DataAnnotations addendum's
  Pattern E record-before-dataset example. No action needed.
