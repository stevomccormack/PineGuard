# P4.2 — "Can it fail" mutation audit of all 14 audit rules

> **Working artifact.** `artifacts/` is gitignored (`.gitignore:9`), so this report is not
> committed. It is reproducible at any time by re-running the two mutation drivers described
> in §4.

- **Date:** 2026-09-07
- **Branch / worktree:** `worktree-audit-cli-rebuild` (`.claude/worktrees/audit-cli-rebuild`)
- **Baseline:** 25 test files, **197 tests passing**, tree clean before and after every mutation.
- **Plan reference:** `docs/ai/plans/audit-cli-rebuild.md` §2.2, §2.3, §4.6, §9.2 row P4.2.

## 1. What this audit is for

Plan §2.3: *"No tests for the auditor. A one-line 'does this rule produce a finding on a
known-bad fixture' test would have caught Rules 03–07 on day one."* The legacy PowerShell
tool's Rules 03/04/05/07 reported PASS every run for months because a quote-escaping bug made
them **structurally unable to emit a finding**. Reading a test and concluding it looks fine is
exactly the review step that failed back then, so this audit does not read — it **mutates**.

For each rule the question is: *if `run()` were broken in the old tool's exact shape, would the
test suite notice?* A rule whose test still passes under that mutation is vacuous.

## 2. Mutation 1 — the old bug's exact shape (all 14 rules)

`return []; // MUTATION` inserted as the first statement of each rule's `run()` body, then
`pnpm -C apps/cli exec vitest run test/rules/<slug>.test.ts`, then `git checkout --` the rule
file. `git status` verified clean before and after every single cycle.

**Result: 14 / 14 rules FAILED as expected. Zero vacuous rules. No fixes required.**

The stronger check is the third column: in **all 14** runs the failure carried the harness's own
diagnostic — *"produced zero findings against its own invalid fixture … this is exactly how the
old audit tool's Rules 03/04/05/07 went silently vacuous for months"*. That proves the failure
came from `expectInvalid` against `invalid/`, not from some incidental boundary assertion that
happened to break.

### 2.1 Note on rules where only one test failed

`doc-links`, `must-collisions` and `ordering` each show a single failure. That is not weakness —
their other tests are `expectValid` (still correctly `[]` when `run()` returns `[]`) and, for
`ordering`, nine pure unit tests of the normalisation table that never call `run()` at all. The
one failure in each case *is* the invalid-fixture assertion, which is the thing under audit.

## 3. Mutation 2 — targeted, realistic bugs (4 rules with subtle logic)

"Return `[]`" only proves a test notices a *completely* dead rule. These four probe whether the
tests would notice a rule that is merely **subtly wrong** — i.e. whether the assertions are
real, or just "any nonzero count".

**Result: 4 / 4 caught, each by a precisely relevant test.**

| Rule | Targeted mutation | Caught? | Caught by |
|---|---|---|---|
| `nullability` | Generic-constraint handling: the `where T : struct` detector matches `child.text === "class"` instead of `"struct"` | **yes** — 5 failed / 4 passed | All three struct/class-constraint boundary tests plus the exact-count test *and* the `valid/` fixture (false positives), i.e. caught from both directions |
| `must-collisions` | Overload heuristic: `isReachableWithSingleArgument` uses `restParameters.some(hasDefaultValue)` instead of `.every(...)` | **yes** — 1 failed / 6 passed | The invalid-fixture test. (`.some([])` is `false` where `.every([])` is `true`, so zero-rest-parameter overloads stop being reachable and the collision disappears.) |
| `ordering` | Normalisation table: the `IN_PREFIX_REMAINDERS` whitelist guard is dropped, so `In` is stripped blindly | **yes** — 1 failed / 10 passed | `does NOT strip 'In' out of the middle of a longer word (word-boundary safety)` — the dedicated unit test for exactly this hazard, which the source comment calls out (`IsInstance` → `stance`) |
| `test-structure` | Check 4 off-by-one: dataset-order filter is `datasetRank(p.name) > 0`, silently dropping `ValidCases` (rank 0) from the comparison | **yes** — 1 failed / 4 passed | `flags InvalidCases declared before ValidCases within an Operation Group (v11 §4.4)` — only the affected one of the four checks broke, and the test pinned it |

The `test-structure` case is the most reassuring: an off-by-one that disabled **one of four**
checks, leaving the other three emitting findings, still failed the suite. A test asserting only
`findings.length > 0` would have sailed past it.

## 4. Reproducing

Two Node drivers (kept out of the repo, in the session scratchpad):

1. `mutate2.mjs` — inserts `return [];` into each rule's `run()`, runs that rule's vitest file
   with `--reporter=verbose`, greps for the harness's invalid-fixture message, reverts via
   `git checkout --`, and asserts a clean tree between cycles.
2. `mutate3.mjs` — the four targeted string substitutions in §3, same revert/verify discipline.

Both abort immediately if the tracked working tree is dirty before a cycle.

## 5. Incidental finding — `.ts` line endings are not pinned (not a P4.2 defect)

Surfaced by the revert half of this audit, worth recording for a later tooling task:

- `core.autocrlf=true`, and root `.gitattributes` lists explicit `text` rules for `*.cs`,
  `*.ps1`, `*.md`, `*.json`, … but **not `*.ts`**, which therefore falls through to `* text=auto`
  → **CRLF on a Windows checkout**.
- Meanwhile `.editorconfig` declares `end_of_line = lf` and Prettier's default `endOfLine: "lf"`
  enforces LF, so `pnpm -C apps/cli exec prettier --check .` **fails on any file git has
  actually checked out on Windows**.
- This bit this audit directly: `git checkout -- <rule>.ts` correctly restored the *content* but
  rewrote it CRLF, and Prettier then flagged all 14 files. Notably `git status` still reported
  clean at that point, so the EOL flip is invisible to the porcelain check the drivers used —
  the mutation reverts were content-correct throughout, just EOL-flipped.
- **Resolved for this worktree** by converting the 14 files back to LF. `git diff --numstat`
  across `apps/cli/src/audit/rules/` is empty — **zero content change vs. HEAD** — and Prettier
  now passes. `git status` shows the 14 as ` M` purely as git's "worktree EOL differs from what
  checkout would produce" marker; there is nothing to stage or commit.
- **Suggested follow-up (not done here — repo-wide line-ending policy is the owner's call):** add
  `*.ts text eol=lf` (and `*.mts`/`*.cts`) to `.gitattributes`. Low urgency while CI for
  `apps/cli` is not yet wired and Linux runners check out LF regardless; it is a Windows
  developer-experience trap, not a current CI break.

## 6. Conclusion

- **14 / 14 rules mutation-tested. Zero vacuous. Zero fixes needed.**
- Every rule's `invalid/` fixture is load-bearing, and every one is asserted through
  `expectInvalid` from `apps/cli/test/support/runRule.ts` — no rule substitutes a weaker bare
  `expect(findings.length).toBeGreaterThan(0)`.
- The four subtle-bug spot-checks confirm the assertions test *behaviour*, not just non-emptiness.
- The class of failure that killed the legacy tool's Rules 03/04/05/07 cannot now reach `main`
  undetected: it fails the suite on the first run.
