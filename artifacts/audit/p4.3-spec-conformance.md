## 2. `test-structure` (Rule51, rewritten)

### Checks verified correct

| Check | Spec | Verdict |
|---|---|---|
| Tests class nests no `public static class` | §5.1 | Correct, and correctly scoped: the Fluent addendum's mandatory `private sealed record Model` / `private sealed class XxxValidator` (its "Model + Validator Pattern") are `private`, so they are not flagged. DataAnnotations' `private sealed record ActionThrowsCase` lives in TestData, not Tests. |
| Every Op Group has a test method | §4.5 bullet 1 | Correct **after fix** (was over-strict — §2.2). |
| Method order matches group order | §4.5 bullet 2 | Correct. |
| No orphan `_BehavesAsExpected` method | §4.5 | Correct **after fix**. |
| `ValidCases` → `EdgeCases` → `InvalidCases` | §4.4 item 1 | Correct. The single-`Cases` rollup (Core/Fluent/DA per §4.1's table) is exempt from ordering, which is right. |
| No `=> [];` dataset | §4.1 note 2, §10.3 | Correct. |

### Gap A — false positive: underscore-variant method names (FIXED)

`docs/ai/specs/fluent-validation/unit-test.md`, "Nullable vs Non-Nullable Variants", pairs
Operation Group **`EvenNonNullable`** with test method **`Even_NonNullable_BehavesAsExpected`**.
The rule compared the two literally, so every such pair produced *two* findings (a "missing
method" for the group and an "orphan" for the method). 35 pairs on `main`
(`IsDefaultInt32` ↔ `IsDefault_Int32_BehavesAsExpected`, `IsEvenLong` ↔ `IsEven_Long_BehavesAsExpected`, …).

**Fix**: group and method are matched with `_` removed from both sides.
`apps/cli/src/audit/rules/test-structure.ts` — `squash()`, used in `indexByBase`,
`squashedGroupNames` and the ordering pass.

### Gap B — false positive: throws-only Operation Groups (FIXED)

`unit-test.md` §8.3 splits its own canonical `Parse` group into a
`_BehavesAsExpected` / `_ThrowsAsExpected` pair, and
`docs/ai/specs/data-annotations/unit-test.md` "Pattern E — TypeMismatch Throws" defines a
group whose **only** method is `<Attr>_TypeMismatch_ThrowsExpected`. The rule required a
`_BehavesAsExpected` method unconditionally, so 10 spec-conforming groups on `main` were
flagged — including four DataAnnotations Pattern-E groups
(`PhoneNumberTypeMismatch` → `PhoneNumber_TypeMismatch_ThrowsExpected`, …).

**Fix**: a group is also satisfied by a `<Group>…Throws[As]Expected` method
(`THROWS_SUFFIX`, `throwsCompanionsFor`). Nothing else satisfies it — a group whose only
method is `<Group>_ShouldReturnExpected` is still a finding, which is what §5.1's
"Do **NOT** use `ShouldReturnExpected`, `ShouldThrowExpected`, `ReturnsExpected`, or any
other naming pattern" requires.

### Gap C — false negative: `sealed` Tests class (FIXED)

§5.1: "Test class `XxxTests` must be `sealed`". Not checked. **6 live violations** on `main`,
all in `tests/PineGuard.MustClauses.UnitTests/` (`MustDateOnlyClausesTests`,
`MustDateTimeClausesTests`, `MustDateTimeOffsetClausesTests`, `MustFilePathClausesTests`,
`MustResultTests`, `MustStringClausesTests`). New `not-sealed` check.

### Gap D — false negative: `public static void` test methods (FIXED)

§5.1 ("Test methods must be **instance** methods declared `public void`") plus all five
addenda ("Instance methods — `public void` (not `public static void`)"). Not checked.
Zero live violations, but it is a realistic PR regression — a `static` test method silently
loses access to the layer base's `AssertResult`. New `static-method` check.

### Fixtures added

- `invalid/BarRulesTests.cs` + `BarRulesTestData.cs` — non-sealed class **and** a
  `public static void` test method.
- `boundary/VariantRulesTests.cs` + `VariantRulesTestData.cs` — the two spec-sanctioned
  shapes from Gaps A and B, asserted to produce zero findings.

### Residual (real debt, not a rule bug)

1036 findings remain, dominated by `missing: 790` / `orphan: 158` — genuine §4.5/§5.1
method-naming drift, overwhelmingly in projects outside the five layers
(`PineGuard.Analyzers.UnitTests`, `PineGuard.AspNetCore.UnitTests`,
`PineGuard.Core.UnitTests/Common` and `/Utils`) whose methods use
`_ReturnsExpected` / `_ShouldReturnExpected` / free-form names. This is real per §5.1 —
but see §7.3 for the scoping question it raises for the baseline.

## 3. `test-records` (Rule52, rewritten)

### Checks verified correct

The per-layer scoping was re-derived against **every** addendum, not just the ones the
original implementer cited:

| Layer | Addendum text | Rule behaviour | Verdict |
|---|---|---|---|
| Core | §4 "No custom record definitions in TestData — `RuleCase<T>` is used directly", but the root §4.2 "Standard Definitions" and §8.2's `Parse` do define records | Requires a real base, not a ban | Correct — the Core addendum's "no custom records" applies to *scenario-backed* Op Groups; §8.2's `Parse` (Core, `FooRulesTestData`) defines `ValidCase`/`InvalidCase` outright. |
| Must | "Must tests use `MustCase<TValue>` — **no custom record definitions**" | Ban | Correct. 187 live findings. |
| Guard | "Guard tests use `GuardCase<TValue>` — **no custom record definitions**" | Ban | Correct. |
| Fluent | "Explicit Prohibitions: No custom case records: only `FluentCase<TValue>`" | Ban | Correct, with the P4.3 narrowing below. |
| DataAnnotations | "`DataAnnotationCase` is the **only** allowed case type" + Pattern E | Ban + throws exemption | Correct. All 17 real `ActionThrowsCase` declarations exempted. |
| `PineGuard.Testing.UnitTests` | n/a — it *tests* `BaseCase`/`ValueCase<>` | Exempt entirely | Correct. |
| "(Other)" packages | Root §2.1 lines 55–61 | Treated as Core-like (needs a real base) | Correct. |

Scoping by `*.UnitTests` path segment matches the addenda's own `applies_to` globs. Only
`*Case`-suffixed records are considered, which correctly leaves the repo's
value-object records (`Widget`, `Order`, `FailureExpectation`) alone in every layer.

### Gap A — false positive: `ThrowsCase<>` records in a banning layer (FIXED)

The exemption was hardcoded to *DataAnnotations* + the literal name `ActionThrowsCase`.
Four FluentValidation adapter-infrastructure TestData files declare the identical
`private sealed record ActionThrowsCase(...) : ThrowsCase<Action>(...)` for the identical
reason and were flagged (7 findings): `FluentMustValidatorTestData.cs`,
`MustChildValidatorTestData.cs`, `RuleBuilderExtensionTestData.cs`,
`ValidationResultExtensionTestData.cs`.

The Fluent prohibition is textually scoped: *"Never define `ValidCase`, `NullCase`, `Args`,
or any other local record extending **`ReturnCase<T, bool>`**"*. Every layer case type is
`ReturnCase<,>`-derived and carries a layer `Expected` (`fixture.md` §3). A `ThrowsCase<>`
record carries an `ExpectedException` instead and has no shared layer equivalent to
replace — it is the hand-built shape the *root* spec keeps for throwing members
(§4.2 "Standard Definitions" patterns 2 and 3; §8.2's `FooRulesTestData.Parse`;
§8.3's `Parse_ThrowsAsExpected`) and that the DataAnnotations addendum sanctions by name.

**Fix**: exempt the *shape* (`isThrowsCaseRecord`) in every layer instead of one hardcoded
DataAnnotations record name. `apps/cli/src/audit/rules/test-records.ts`.
Fixture added: `valid/tests/PineGuard.FluentValidation.UnitTests/FluentThrowsExtensionsTestData.cs`.

### Gap B — flagged, not changed: the `ValueCase<>`/`BaseCase` prohibition (§7.4)

46 of the 282 remaining findings are `wrong-base` — Core records inheriting `ValueCase<T>`
or `BaseCase` directly. **No spec text forbids this.** See §7.4.

## 4. `test-orphans` (Rule53, rewritten) — the worst offender

### The problem

79 findings on `main`, of which **77 were false positives**. Two distinct causes:

**Cause 1 — the family-per-file convention (55 findings).** Every
`PineGuard.DataAnnotations` source file declares a *family* of attributes and no type
shares the file's own name (`BitWiseAttributes.cs` declares `HasAllBitsAttribute`,
`HasAnyBitsAttribute`, …). The paired test file is named after the **file**. This is not
an accident: `docs/ai/specs/data-annotations/unit-test.md`'s own **"Canonical Example
(StringBoolAttributes)"** is `StringBoolAttributesTests.cs` ↔ `StringBoolAttributes.cs`,
whose declared types are `TrueStringAttribute` / `FalseStringAttribute`. **The rule was
flagging the addendum's own canonical example.** The same shape hits
`FixtureSmokeTests`, `BaseCasesTests` and the Core `StringRules*`/`StringUtility*` files.

**Cause 2 — enums are types too (1 finding).** `findTypeDeclarations` covered
`class`/`record`/`struct`/`interface` only, so
`tests/PineGuard.Core.UnitTests/Common/InclusionTests.cs` → `src/PineGuard.Core/Common/Inclusion.cs`
(`public enum Inclusion`, which `fixture.md` §9 lists among the repo's constant-bearing
types) was reported as an orphan.

**Cause 3 — dotted partial files (12 findings).** `fixture.md` §10 documents the
`StringRules.Bool.cs` split; the repo's paired test file is `StringRulesBoolTests.cs`
(dots removed). The subject type is the whole `StringRules` partial, so a pure
type-name lookup could never resolve it. The *old* PowerShell rule handled this with its
dot-stripping normalisation; the rewrite dropped it.

### Fixes

1. `apps/cli/src/audit/parsing/csharp.ts` — `enum_declaration` added to
   `TYPE_DECLARATION_NODE_TYPES`, `"enum"` added to `TypeDeclarationKind`.
   (`findTypeDeclarations` has exactly one consumer, this rule, so no other rule moves.)
2. `apps/cli/src/audit/rules/test-orphans.ts` — after the AST type lookup fails, fall back
   to the candidate projects' source **file** basenames, matched exactly and with `.`
   separators removed. Restricted to the same resolved project set (`src/<Pkg>` +
   `<ProjectReference>` targets), never repo-wide.

Keeping the filename match **as a fallback** cannot reintroduce the old rule's false
positives: those were cases where the filename match *failed* (`Baz.Core.cs` for
`class Baz`), which the AST lookup now answers first.

### Verified: the real-drift signal is preserved

Both cases the plan (§2.4, §8) explicitly requires this rule to keep catching still fire:

- `MustStringNumberClausesTests.cs` — neither a type nor a file called
  `MustStringNumberClauses` exists (the source is the plural `MustStringNumbersClauses.cs`).
- `FluentDateExtensionsTests.cs` — subject moved to `FluentSqlDateTimeExtensions.cs`.

The boundary fixture's deliberate singular/plural near-miss (`WidgetTests.cs` vs
`class Widgets` in `Widgets.cs`) and the invalid fixture (`QuxTests.cs` vs `QuxHelpers.cs`)
both still fail, unchanged.

Remaining 11 findings are all plausible real drift or allowlist candidates
(`PathUtilityTests`, `AttributeNullTests`, `BaseAttributesTests`,
`ErrorMessageAttributesTests`, `FluentMiscExtensionsTests`, `CaseRecordTests`,
`ExpectedTests`, `RuleScenarioExtensionsTests`, `FixtureSmokeTests`, plus the two above).

### Fixtures added (all under `valid/`)

- `src/Grouped/GroupedAttributes.cs` + `tests/Grouped.UnitTests/GroupedAttributesTests.cs` —
  the family-per-file convention (Cause 1).
- `src/Split/Split.Bool.cs` + `tests/Split.UnitTests/SplitBoolTests.cs` — the dotted
  partial split (Cause 3).
- `src/Enums/Shapes.cs` (declaring `enum Mode`) + `tests/Enums.UnitTests/ModeTests.cs` —
  the enum case (Cause 2). The file is deliberately **not** `Mode.cs`, so only the
  type-declaration lookup can resolve it.

## 5. `test-tuples` (Rule54, rewritten)

### The gap: two of three in-scope tuple shapes were invisible

§4.3 governs the tuple that carries a multi-parameter method's inputs. That tuple appears
in three shapes; the rule saw only the first:

| Shape | Sites on `main` | Seen before? |
|---|---|---|
| A `*Case` record's `Value` primary-constructor parameter | ~239 | Yes |
| The first type argument of a `*Case`/`*Scenario` generic — `TheoryData<RuleCase<(int value, int min, int max)>>`, `RuleScenario<(…)>` | ~1,533 in `*TestData.cs` | **No** |
| A fixture `public static readonly (…) Field` and its `RuleScenario<(…)>` arrays | ~685 | **No** (fixture files were entirely out of scope) |

Shape B is the shape **every §4.3 example in the spec is written in** (§4.3's two canonical
examples, §8.1's `IsBaz`, `fixture.md` §11.4). A PR introducing
`RuleCase<(string? val, int len)>` — abbreviated *and* not matching the source parameter
names — was never flagged.

Shape C was out of scope because the rule only read `*TestData.cs`. But root §9.3 states
the fixture field convention in the same terms and points straight back at §4.3
("Tuple element names: **camelCase**, **exact parameter names** from the method under test
(per §4.3)"), and `fixture.md` §11.4 repeats it verbatim. Fixtures are where the tuple is
*defined*, so a wrong name there propagates into every layer's TestData.

### Fixes

`apps/cli/src/audit/rules/test-tuples.ts`:

- New `collectTupleSites()` gathers all three shapes; `checkTupleSite()` replaces
  `checkRecord()`.
- File scope widened to `tests/PineGuard.Testing/Fixtures/**` alongside `*TestData.cs`.
- `resolveSourceMethod()` now strips a trailing `Fixtures` as well as `TestData`
  (`StringRulesFixtures` → `StringRules`), mirroring `fixture.md` §9.2's
  "Inner class | Matches the Core Rules method name" convention. Every unresolvable step
  still degrades to a silent skip of check 2 only.
- `apps/cli/src/audit/parsing/csharp.ts`: `toTupleTypeInfo(node)` extracted and exported
  (`findTupleTypes` now maps over it) so a single tuple node can be read.

**Guard against over-reach**: only tuples in a *declaration's type position* count.
`EXPRESSION_POSITION_ANCESTORS` excludes a record's `base_list` (a two-line record
restates its `Value` type there — double reporting) and every expression position. That
last exclusion was added after the first run produced 70 findings against
`new RuleScenario<(TimeSpan, TimeSpan, Inclusion)>(…)` projection intermediates inside
`.Select(…)` in `FluentTimeSpanExtensionsTestData.cs` / `GuardTimeSpanClausesTestData.cs`,
whose *declared* dataset type one line up is correctly named — §4.3 governs the
declaration, so those would have been false positives.

### Result

339 → 879 findings (`exact-name: 617`, `camel-case: 262`, `unnamed: 0`). Spot-verified
correct, e.g. `DictionaryRulesFixtures.HasAnyKey` names its first tuple element
`dictionary` where `DictionaryRules.HasAnyKey(IDictionary<TKey,TValue>? value, …)` calls it
`value` — a genuine §4.3 "no renaming" violation, in a fixture, propagating to every layer.

### Fixtures added / extended

- `valid/` — a `TheoryData<RuleCase<(int value, int min, int max)>> Cases` property (shape
  B, clean) and `tests/PineGuard.Testing/Fixtures/FakeClausesFixtures.cs` (shape C, clean).
- `invalid/` — a PascalCase `TheoryData<RuleCase<(string? Value, int Length)>>` (shape B
  can fail).
- `boundary/` — `tests/PineGuard.Testing/Fixtures/FakeClausesFixtures.cs` with a renamed
  (`lower` vs `min`) but valid-camelCase element, proving the exact-name check fires in a
  fixture file and resolves through the `Fixtures` suffix.

## 7. Flagged for a decision (NOT resolved here)

### 7.1 `test-files` `[FactAttribute]` / `[Fact, Trait(...)]` blind spot — plan vs spec

- **Spec**: §1 "`[Fact]` … disallowed"; §11 "no `[Fact]` in `*Tests.cs`", enforced by Rule50,
  which "gates pull requests".
- **Rule**: `FACT_ATTRIBUTE_PATTERN = /\[\s*Fact(\s*\(|\s*\])/` matches only `[Fact(` and
  `[Fact]`. `[FactAttribute]` and `[Fact, Trait("x","y")]` are the same attribute and slip through.
- **Why not fixed**: the rule's doc comment calls this a "known, intentionally-preserved"
  legacy blind spot under P2.10's explicit exact-parity brief, plan §4.3 records
  `Rule50 → test-files` as "Same", and **P4.1 is concurrently asserting byte-parity on this
  rule** ("expected: … `test-files` identical"). Changing it now would invalidate that run.
- **Zero risk when it is changed**: 0 occurrences of either form on `main` today, so
  widening to `/\[\s*Fact(Attribute)?\s*(\(|\]|,)/` plus a `,\s*Fact` alternation is a no-op
  against the current tree.
- **Decision needed**: does the CI gate follow the spec (widen) or the parity mandate
  (keep)? Recommend widening **after** P4.1 lands.

### 7.2 `[InlineData]` — root §1 vs §11's enumeration

§1 bans `[InlineData]` outright. §11 enumerates exactly two machine-checked rules and
scopes the first as "`[Theory]`-only parameterization (**no `[Fact]`** in `*Tests.cs`)" —
the parenthetical omits `[InlineData]`. `tests/PineGuard.DataAnnotations.UnitTests/ErrorMessageAttributesTests.cs`
uses it in 5 places today. Adding the check would put new findings on the **one gating rule**.
Decision needed: is §11's parenthetical the operative scope, or is §1?

### 7.3 §5.1's method-naming rule — scope for the baseline

`test-structure` reports **948** `missing`/`orphan` findings on `main`. Almost all are
methods named `_ReturnsExpected`, `_ShouldReturnExpected`, `_Checks`, `_EdgeChecks` or
free-form, in projects **outside** the five layers — `PineGuard.Analyzers.UnitTests`
(analyzer diagnostics), `PineGuard.AspNetCore.UnitTests`, and
`PineGuard.Core.UnitTests/{Common,Utils}` (range/enumeration value types, not Rules).
§5.1 forbids these unambiguously and `applies_to` is `tests/**`, so the findings are
*correct*. But §5.1's naming rule is written for the layer-base architecture
("Each test method takes a single layer case parameter named `tc` … and delegates its
assertion to `AssertResult(tc, result)`"), which those projects do not use.

Decision needed: baseline all 948 as-is, or narrow `test-structure`'s §4.5/§5.1 naming
half to the five layer projects (as `test-records` already does for its own checks, per
plan §8's "Scope by test project, not repo-wide")?

### 7.4 `test-records`: the `ValueCase<>` / `BaseCase` prohibition has no spec basis

`RAW_INFRASTRUCTURE_BASES` flags a case record inheriting `ValueCase<T>` or `BaseCase`
directly — 46 findings, all Core (`ThrowHelperTestData`, `MustResultTestData`,
`MustValidatorTestData`, `DateTimeOffsetRangeTestData`, …). This came from the legacy
Rule52. **No spec text supports it**: root §2.2 lists `ValueCase<TValue>` ("Case with a
single `Value` input") and `BaseCase` as first-class members of the shared hierarchy, not
as deprecated (unlike `IsCase<T>`/`HasCase<T>`, which §2.2 and `fixture.md` §3 *do* mark
superseded). The rule's own justification ("those skip the `Expected`-carrying shape the
assertion helpers rely on") is engineering reasoning, not spec text — and it is not always
true: a void/throwing member's case has no `Expected` to carry.

Decision needed: is this a real convention the spec should be amended to state, or should
the check be dropped?

### 7.5 Spec-vs-spec: §4.1's "never any other names" vs `fixture.md`'s own datasets

`unit-test.md` §4.1: *"Where a split is used, the dataset names are `ValidCases`,
`EdgeCases`, `InvalidCases` — **never any other names**."*

But `fixture.md` — which wins over §4 — uses two other names itself:
- §12.2 (inverted guards, nullable variants): `public static TheoryData<GuardCase<string?>> NullCases => …`
- §11.6 (ad-hoc cases): `public static TheoryData<DataAnnotationCase> AdHocCases => …`

`test-structure` currently ignores unrecognised dataset names, so there is **no false
positive today** — the contradiction only matters if anyone later adds a
"no unknown dataset names" check. Recommend `fixture.md` wins (it says so itself) and that
§4.1's absolute is softened to name `NullCases`/`AdHocCases` as sanctioned exceptions.

Related, unresolved and currently unchecked: `IsEmpty_AdHoc_BehavesAsExpected`-style
methods (a second `_BehavesAsExpected` method per group, consuming `AdHocCases`) are
reported as orphans by `test-structure` — 158 findings include several. §4.5 says one
method per group; `fixture.md` §11.6 implies `AdHocCases` sits inside the group. Left as
findings pending 7.3's scoping decision.

### 7.6 Spec-vs-spec: §4.4 "datasets first, records last" vs DataAnnotations Pattern E

`unit-test.md` §4.4: *"Datasets first, records last."* The DataAnnotations addendum's
"Pattern E — TypeMismatch Throws" shows the **opposite** in its own example: the
`private sealed record ActionThrowsCase` is declared *before* the `Cases` property, and the
addendum's Prohibited-Patterns table reinforces the placement ("`ActionThrowsCase` at outer
TestData class level" → wrong; inside the Op Group → right) without addressing ordering.

81 Op Groups on `main` declare a record before a dataset; the DataAnnotations
`*TypeMismatch`/`*WrongType` groups among them are following their own addendum.
**No §4.4 record-ordering check was added** because implementing it requires resolving this
first. Decision needed: does the DataAnnotations addendum override §4.4 for its layer
(the root spec's §2.1 precedence rule says yes), and should the addendum say so explicitly?

### 7.7 Minor: the addenda's own examples violate root §1's brace/wrap rule

Root §1: *"the `: BaseXxxUnitTest(output)` inheritance clause MUST appear on a new line,
indented 4 spaces"*. The Must, Guard, Fluent and DataAnnotations addenda all show it on
one line in their canonical examples
(e.g. `public sealed class GuardBoolClausesTests(ITestOutputHelper output) : BaseGuardUnitTest(output)`).
Not machine-checked by any rule (no rule covers §1's formatting half) and not proposed as
one — recorded so the addenda can be corrected in a docs pass.
