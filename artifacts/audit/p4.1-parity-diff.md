## 3. Flagged for follow-up

### 3.1 **UNEXPLAINED, MUST RE-MEASURE (high)** — two full-catalog runs under-reported

The first full run of `pineguard audit --no-baseline --format json` reported **`must-usage`: 0
findings** and a total of 2358. Every subsequent run reports `must-usage`: 206 and a total of 2564.
Six full-catalog runs were made against an unchanged tree:

| Run | Format | Concurrent old tool? | `must-usage` | `doc-links` | Total |
|---|---|---|---|---|---|
| 1 | json | yes | **0** | 173 | **2358** |
| 2 | pretty | no | 206 | **172** | **2563** |
| 3 | json | no | 206 | 173 | 2564 |
| 4 | pretty | yes | 206 | 173 | 2564 |
| 5–7 | pretty | no | 206 | 173 | 2564 |

**Two anomalies in seven runs, both under-reporting.** Neither reproduces on demand: running the
old tool concurrently on purpose (run 4) produced a clean result, and `doc-links` run *alone*
returns 173 every time, so the 172 only occurs in a multi-rule run. `must-usage` run alone returns
206 every time; run alongside all six other library rules, 206; alongside the five testing rules,
206; paired with `doc-links` or `surface-parity`, 206 — the collapse to 0 has been seen exactly
once, in the 14-rule run.

**The most likely explanation is the shared worktree, not the engine.** Other agents were editing
`apps/cli/src/audit/**` throughout this window — `must-usage.ts`'s own mtime moved at 10:16, minutes
after the anomalous 10:11 run, and `csharp.ts` (the shared tree-sitter module every C#-parsing rule
imports) was rewritten at 11:53. A `tsx` process that loads a module mid-write, or loads a
transiently inconsistent pair of modules, would produce exactly this: a one-off wrong answer that
never reproduces. P4.2's independently-run mutation testing (commit `7bf9ee7`) separately concludes
that **none of the 14 rules is vacuous**, including `must-usage`, which corroborates "artefact of a
moving tree" over "the rule is broken". **This is therefore recorded as unexplained-and-must-be-
re-measured, not as a confirmed engine race.** Re-run the full catalog ≥3 times on a quiet tree
with no other agent active before P6.1 snapshots the baseline; if the anomaly does not recur, close
this item.

Why it still must not be waved through:

- **The direction is always fewer findings.** An audit gate that intermittently under-reports is
  worse than one that over-reports; a flaky green is invisible.
- **P6.1 snapshots the baseline from exactly this command.** A snapshot taken during an anomalous
  run would silently bake in a wrong ratchet floor for the affected rule — and because
  `applyBaseline` matches keys exactly, a *missing* baseline entry is the safe direction but a run
  that produced 0 findings would produce *no* entries and then the rule becomes a hard gate against
  a debt of 206. Either way the baseline would be wrong.
- **The rule that failed is specifically the one whose entire purpose is not being vacuous.**

Two things a fix agent should look at regardless of what the re-measurement shows:

1. **`src/audit/engine.ts:398` runs all rules under one `Promise.all`, over process-wide mutable
   parser state.** `src/audit/parsing/csharp.ts` holds a single shared `Parser` instance
   (`parserPromise`) and a single `parseCache` `Map`, and every rule interleaves `await`s through
   them. If the re-measurement *does* reproduce the anomaly on a quiet tree, this is the first
   place to look. Note it would not explain the `doc-links` wobble on its own — `doc-links` uses
   remark, not tree-sitter.
2. **`src/audit/rules/must-usage.ts:249` turns any such glitch into a silent PASS**, whatever its
   cause — this one is a real defect independent of §3.1's outcome. The rule
   opens with:

   ```ts
   const mustMethods = await collectMustMethods(ctx);
   if (mustMethods.length === 0) {
       return [];
   }
   ```

   That is structurally the *same failure mode* as legacy Rule03/04/05 — "I found zero Must clauses,
   therefore zero are unused, PASS" — even though the *cause* (the `\\.` regex bug) is genuinely
   gone. A rule that cannot find its own subject population should emit a diagnostic finding, not
   return clean. The same shape should be checked in the sibling rules. **This is a design defect
   independent of whatever caused the flake, and it is the reason the flake was invisible in the
   summary output.**

*No rule implementation was modified as part of this task, per P4.1's brief.*

### 3.2 **POTENTIAL REGRESSION (high)** — rules audit the CLI's own test fixtures, and one is a CI gate

Three rules report findings against `apps/cli/test/fixtures/**` — the VIBE fixture trees that exist
*specifically to be invalid*:

| Rule | Gate? | Findings inside `apps/cli/test/fixtures/` | Of total |
|---|---|---|---|
| `doc-links` | **yes** | 16 | 173 |
| `test-orphans` | no | 11 | 90 |
| `test-structure` | no | 7 | 1117 |

`doc-links` is `gate: true` and is one of the three rules P5.2 will wire into CI. Sixteen of its
gate-blocking findings are deliberately broken links inside
`apps/cli/test/fixtures/doc-links/invalid/README.md`,
`apps/cli/test/fixtures/surface-parity/*/.fakepi/AGENTS.md` and friends — content authored to make
those rules fail. Gating merges on a rule's own negative test data is wrong, and it also means the
count moves whenever a fixture is edited. `apps/cli` adds 22 `doc-links` findings in total (16
fixtures + 6 from the CLI's own `README.md`s, which are ordinary real drift and should stay).

The fix is a scope exclusion for `apps/cli/test/fixtures/**` — most naturally in
`apps/cli/config/exceptions.json` as part of P5's cascade, or in the engine's context build. It is
